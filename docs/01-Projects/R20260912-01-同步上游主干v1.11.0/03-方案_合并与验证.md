# 03-方案：合并策略与验证

**日期**：2026-09-12

## 一、方案选型

需求是「把 `origin/main` 合进 `dev-creator`」。三条路：

| 方案 | 做法 | 判定 |
|------|------|------|
| **A. stash → merge → pop**（采用） | 把在途改动暂存，合并完成后原样还回 | ✅ 保留分叉历史、可追溯、可回退；在途工作零丢失 |
| B. 在临时分支合并再切回 | 多一条分支，验证后切回 | ✗ 多一层状态，且最终仍要把结果搬进 `dev-creator` |
| C. 直接 `git pull` | 工作区脏、`handlers.ts` 双方都改，必冲突且失败 | ✗ 不可用 |

**选 A**，理由是 `dev-creator` 与 `origin/main` 的 merge-base 正是 `3957fa24`（`dev-creator` 的基线），所以 `origin/main` 是「从基线长出去」的那一支 —— 合并后不会产生第二套分叉乱账。同时 A 方案能把在途工作完整隔离，符合「不破坏现有体验」。

**为什么不用 `--no-ff` 之外的策略**：本次是有真实分叉的正常合并，保留合并提交即可；不 squat、不 rebase（已经 push 不出去，但 rebase 61 个提交会重写本地 6 个提交的历史，收益为零）。

## 二、执行步骤

### 步骤 1 — 备份（可回退的前提）

```bash
git diff > <runtime>/openscreen-backup/dev-creator-tracked-<ts>.patch
```

只备份**已跟踪**的改动。未跟踪的 `electron/logging/`、`docs/01-Projects/R20260908-01-…/` 不 stash —— 先确认 `origin/main` 里没有这两个路径（实测：无 `electron/logging`，无 `docs/01-Projects`），不会被合并覆盖。

### 步骤 2 — 暂存在途改动

```bash
git stash push -m "wip: logging (pre origin/main merge)" \
  electron/ipc/handlers.ts electron/main.ts electron/stt/index.ts
```

**只 stash 已跟踪文件**，未跟踪目录留在原地（不参与合并，也就不会丢）。

### 步骤 3 — 合并

```bash
git merge origin/main --no-edit
```

### 步骤 4 — 解冲突

| 文件 | 处理 | 依据 |
|------|------|------|
| `package.json` | 取上游 `1.11.0` | 上游是发布号；`build:win:portable` 经自动合并已保留 |
| `package-lock.json` | 取上游 `1.11.0`（2 处） | 与 `package.json` 三方一致 |
| `AGENTS.md` | **保留本地重写版** + 套用上游那 1 行 macOS 内容保护修正 | 上游改动仅 1 行，本地是整篇重写，取本地为主体 |

**`AGENTS.md` 那一行的具体内容**：macOS 内容保护段从「ScreenCaptureKit 目前传 `[]`，代价是 HUD 可能进录像」改为「原生 helper 现在真的通过 `SCContentFilter(excludingWindows:)` 排除 HUD 与 Notes，普通窗口仍可录」。本地重写版继承了旧描述，直接取本地会丢这条上游事实，所以必须套用。

### 步骤 5 — 还原在途工作

```bash
git stash pop
```

见 §三。

## 四、原生二进制探测方案（本次沉淀的方法）

AGENTS.md 要求「date the binary against the commit **and** search it for a string the change introduced」，且**必须同时跑控制串**。落成可复用步骤：

### 1. 选标记串：必须是**生产代码路径**的

```bash
# 列出某提交在生产代码路径中新增的字符串（行号 < mod tests 起始行）
# 原理：先取 mod tests 起始行，再只保留首次出现位置小于它的串
```

判据**三条**（第三条是实测踩出来的，见 `02-分析_上游变更影响.md` §六）：
- 该串在 **基线版本中不存在**（`git show <base>:<file> | grep`）
- 该串**首次出现行号 < `mod tests` 起始行**（否则 release 构建里根本没有它）
- 该串所在函数**真的被调用**（无调用者会被链接器剥掉，重编也探不到）

### 2. 选控制串：基线/现在都有、且必然编译进去的

### 3. 探测（Git Bash 无 `strings`，用 `grep -a`）

```bash
B=electron/native/bin/win32-x64/compositor_view.node
grep -aqF "<标记串>" "$B"   # 期望 HIT
grep -aqF "<控制串>" "$B"   # 必须 HIT，否则本次探测无效
```

### 4. 判读

> **关键：重编前后各探一次。** 单次读出只能证明「这个串在不在」；**「ABSENT → HIT」的翻转才是「重编真的把新代码编进去了」的直接证据**。流程固定为两步：构建前探一次记基线（应 ABSENT）→ 构建后探同一串（应变 HIT）。

| 标记 | 控制 | 结论 |
|------|------|------|
| HIT | HIT | 二进制**包含**该改动 |
| ABSENT | HIT | 二进制**落后**，不含该改动 |
| 任意 | ABSENT | **本次探测无效**，什么都没学到 —— 停下来修检索方法 |

### 本次实测（完整闭环）

| 对象 | 构建前 | 构建后 | 判定 |
|------|--------|--------|------|
| `compositor_view.node` 有效标记 `no decoder for codec_id` | ABSENT（控制串全 HIT） | **HIT** | 旧缺失 → 新包含 ✅ |
| `compositor_view.node` 哈希 / mtime | `8a7b66a1…` / 09-08 05:59 | `d57f91f1…` / 09-12 16:27 | 确已重编 |
| `wgc-capture.exe` | mtime 09-08 00:13（早于提交 09-10）；该修复未引入新串，改用日期判定 | 哈希 `1f87f7a0…` → `6ce1a4db…` / 09-12 16:25 | 落后 → 已含修复 |
| `cursor-sampler.exe` | `118191f5…` / 09-08 00:13 | **哈希与 mtime 均未变** | 正确——其源码本次合并未动 |
